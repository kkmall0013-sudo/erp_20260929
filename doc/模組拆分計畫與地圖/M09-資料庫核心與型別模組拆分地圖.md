## 一、現況痛點診斷（拆解前盤點）

1. **逾一萬四千行的資料庫巨無霸單體檔 (`src/db/sqlite.ts`, 14,476 行)**：
   - 單一檔案同時混寫 `initSqlJs` 上下文狀態、`CREATE TABLE` 核芯與業務 DDL、欄位升級補丁、種子資料初始化、郵遞區號字典、公司/銀行專戶、單據編碼自癒、案場/預算夥伴、聯絡明細/名片/支票、進貨/報價、發票/AP/出納/支票/AR/暫收預收、RBAC 三層權限與帳號生命週期、金庫軟刪除與 SQL/JSON 備份還原。
   - 任何局部調整皆須面對 630KB 巨檔與 AI 上下文視窗截斷風險，違反第 16 章 L4 資料存取層警戒上限（≤ 900 行）。
2. **千行全域型別單檔 (`src/types/erp.ts`, 1,158 行)**：
   - 所有跨模組介面、Enum、聯合型別全部集中於單一檔案，缺少領域邊界，維護時難以快速定位對應模組型別。
3. **嚴格有向無環圖 (Acyclic DAG) 拆解防呆挑戰**：
   - 拆分 29 支模組時，必須避免跨倉儲互相呼叫形成循環依賴（例如：`projectRepository` 統計進貨成本時若 `inboundRepository` 又引用 `projectRepository` 將構成循環）。
   - 解法：`inboundRepository` 對 `projects` / `business_partners` 採直接輕量 SQL 讀取；會計與出納沿 `invoiceAndTaxRepository ➔ apReconciliationRepository ➔ paymentAndCheckRepository` 單向遞進；AR 與資金池沿 `invoiceAndTaxRepository ➔ arRepository ➔ treasuryPoolRepository` 單向遞進；RBAC 沿 `rbacGroupRepository ➔ rbacUserRepository ➔ rbacUserLifecycleRepository` 單向遞進；入口 Barrel `sqlite.ts` 則僅保留 `getCashFlowMetrics()` 與純 `export *`，實現 0 循環依賴與 0 重複匯出衝突。

## 四、拆分計畫與執行過程紀錄（過程日誌 & 第十六章審計總結）

- **步驟 1（型別域層前置拆解）**：✅ 將 1,158 行的 `src/types/erp.ts` 按五大領域拆為 5 支獨立 `.ts` 檔（109~367 行），並保留 `erp.ts` 為 8 行純轉匯出入口。
- **步驟 2（SQLite 核心引擎分層獨立）**：✅ 抽離 `dbContext`、`dbConstants`、`schemaCore`、`schemaOperations`、`dbIntegrity`、`dbIntegrityUsersAndFinance`、`dbSeed`、`dbInit` 共 8 支核心檔，消除頂層狀態與 DDL 混雜問題。
- **步驟 3（21 支領域倉儲嚴格無循環拆分）**：✅ 依 `Tier 3a ➔ Tier 3b ➔ Tier 3c` 拓撲順序完成 21 支 Repository 抽離，透過符號比對驗證 **213 個原匯出符號 0 遺漏、228 個總匯出符號 0 撞名重複**，並將 `src/db/sqlite.ts` 瘦身為 84 行相容門面。
- **步驟 4（第十六章規範與沙盒零原生彈窗全庫審計）**：
