# 🏛️ ERP 系統全端重構專案：Phase 1 核心架構與資安防禦總綱 (Prisma 旗艦定版)

**文件定位**：本文件為 Phase 1 (Auth, Identity & PBAC) 之最高指導總綱，完美整合業務需求 (BRD)、技術架構 (HLD) 與開發鐵律 (ADR)。
**核心精神**：徹底屏棄傳統套裝軟體之單一公司資料孤島模型，導入兼具「實務彈性（跨公司發票調度與代付）」與「強硬內控（二維權限矩陣、幽靈員工物理隔離、零時差撤權）」的金融級底層架構。

---

## 壹、 業務需求與實務情境白皮書 (BRD)

### 1. 認證機制與會話管理 (Authentication & Session)
* **實務痛點與市場對標**：傳統雲端 ERP 頻繁發生瀏覽器重整（Refresh）導致 Token 遺失而被迫重新登入的低級體驗。本系統採用自建 JWT 機制。
* **安全性與權限鎖**：Token 強制封裝於伺服器核發的 `HTTP-Only Cookie` 中，徹底免疫前端 XSS 腳本攻擊。
* **【新版修正】零信任與毫秒級撤權**：JWT 內部絕對不儲存龐大的權限樹，僅存放使用者與法人標記。權限交由伺服器快取 (Redis) 管理。當 HR 觸發「停權」，後端瞬間清空快取，該帳號點擊下一個按鈕時（0.1 秒內）即遭強制踢下線。

### 2. 人力資源與設備邊界防禦 (Identity & Device Fencing)
* **全域登入模式切換**：系統支援「單一裝置互斥」與「多裝置共存」模式，切換時透過 `tokenVersion` 讓現存 JWT 瞬間失效。
* **設備與 IP 綁定**：依據使用者角色設定 `maxConcurrentSessions` (允許同時登入設備數) 與 `allowedIpRanges` (固定 IP 網段，例如財務帳號僅限辦公室連線)。
* **防洩密匯出水位線**：設定 `dailyExportLimit`，限制特定帳號每日匯出報表或客戶名單的筆數，防堵離職員工惡意打包機密。
* **【新版修正】幽靈員工 (Ghost Employee)**：員工和平離職時，切斷登入權限但完美保留歷史單據血緣。嚴禁直接物理隱藏或軟刪除 (`isDeleted = true`)。

### 3. 三維度權限交集與多公司架構 (User-Company-Role PBAC)
* **三方交集權限矩陣**：員工權限由 `User × Company × Role` 決定。支援「同一個員工，在 A 公司是高階廠長，在 B 公司是唯讀稽核員」。
* **【新版修正】共用主檔機制**：商業夥伴、料件等基礎主檔預設為全集團共用（`companyId` 為 `null`）；而具備金流的交易單據（如採購單）則嚴格綁定單一法人公司。

### 4. 代理人機制 (Delegation)
* **【新版修正】有限制的範圍代理**：高階主管下放權限時，必須強制指定「代理的公司範圍」與「代理的模組（如：僅代理採購簽核）」，嚴防助理越權窺探機密戰情室。

## 貳、 技術白皮書與資料庫架構 (HLD)

1. **Lean JWT + Redis 快取架構**：
   拋棄 Fat JWT 模式。JWT Token Size 控制在 200 Bytes 內，確保工地偏鄉網路極速傳輸。權限驗證依賴 Next.js Middleware / 伺服器端 Redis 進行 O(1) 複雜度的極速比對。
2. **多公司權限扁平化編譯**：
   使用者登入時，系統底層將其所屬的 `UserCompanyAccess` 陣列，編譯為扁平化的 JSON Map，派發給前端 Zustand，實現毫秒級的 UI 元素隱藏。
3. **Null Shared Pattern (共用主檔初始化)**：
   資料庫層級解除主檔對 `companyId` 的強制 Foreign Key 依賴。透過 Null 標記實現全集團可見，完美解決系統初始化 (Seed) 時的雞生蛋死鎖問題。

## 參、 系統開發最高憲法 (ADR) - Prisma 實作鐵律

### 🛡️ RULE-1.1：幽靈員工實體隔離 (`isGhost` vs `isDeleted`)
開發者實作員工離職 API 時，**絕對禁止修改 `isDeleted = true`**（會觸發 Phase 0 全域過濾器導致歷史帳務血緣崩壞）。必須將 `status` 改為 `RESIGNED`，標記 `isGhost = true`，並記錄 `resignedAt`。

### 🛡️ RULE-1.2：範圍代理機制防禦 (Scoped Delegation)
在實作代理簽核 API 時，必須校驗 `delegateScope`。如果代理範圍未包含該模組的代碼（如 `PO_APPROVAL`），即使代理時間有效，伺服器仍必須拋出 403 越權錯誤。

### 🛡️ RULE-1.3：權限與欄位級別遮蔽 (Masked Fields)
`Role` 權限表必須支援 `maskedFields`。若某角色的該陣列包含 `["costPrice", "vendorPhone"]`，後端 API 在回傳資料前，必須主動將這些欄位抹除或替換為 `***`，落實最高防洩密標準。

## 肆、 核心功能要求與 Prisma Schema 契約 (Prisma Schema Models)

```prisma
// ========================================================================
// 💡 公司法人實體表 (多公司架構基石)
// ========================================================================
model Company {
  id                String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  companyCode       String   @unique
  name              String
  taxId             String   @unique
  baseCurrency      String   @default("TWD")
  
  users             UserCompanyAccess[]
  
  isDeleted         Boolean  @default(false)
  version           Int      @default(1)
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  @@map("companies")
}

// ========================================================================
// 💡 使用者模型與資安防禦邊界 
// ========================================================================
model User {
  id                    String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  employeeId            String   @unique
  email                 String   @unique
  name                  String
  passwordHash          String

  // 🛡️ 設備防禦與資安水位線
  tokenVersion          Int      @default(1)
  maxConcurrentSessions Int      @default(3)
  allowedIpRanges       String?  @db.Text
  dailyExportLimit      Int      @default(100)

  // 🛡️ 帳號生命週期狀態機 (RULE-1.1)
  status                String   @default("ACTIVE") // ACTIVE, SUSPENDED, RESIGNED
  isGhost               Boolean  @default(false)
  resignedAt            DateTime?
  reinstatedAt          DateTime?

  // 🛡️ 有限制的代理人機制 (RULE-1.2)
  delegateToId          String?  @db.Uuid
  delegateScope         String[]
  delegateFrom          DateTime?
  delegateUntil         DateTime?

  companies             UserCompanyAccess[]

  isDeleted             Boolean  @default(false)
  version               Int      @default(1)
  createdAt             DateTime @default(now())
  updatedAt             DateTime @updatedAt

  @@map("users")
}

// ========================================================================
// 💡 權限角色矩陣表 
// ========================================================================
model Role {
  id                String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  roleName          String   @unique
  permissions       Json     // 必須符合 RolePermissionsSchema 結構
  
  users             UserCompanyAccess[]

  isDeleted         Boolean  @default(false)
  version           Int      @default(1)
  createdAt         DateTime @default(now())
  updatedAt         DateTime @updatedAt

  @@map("roles")
}

// ========================================================================
// 💡 三維交集權限中介表
// ========================================================================
model UserCompanyAccess {
  id                String   @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid
  userId            String   @db.Uuid
  companyId         String   @db.Uuid
  roleId            String   @db.Uuid

  user              User     @relation(fields: [userId], references: [id], onDelete: Cascade)
  company           Company  @relation(fields: [companyId], references: [id], onDelete: Cascade)
  role              Role     @relation(fields: [roleId], references: [id])

  @@unique([userId, companyId])
  @@map("user_company_access")
}
```

### Zod 強型別驗證標準 (Zod Strong Schema)

```typescript
import { z } from "zod";

// 💡 JWT Payload 瘦身與代理人聲明 
export const JwtPayloadSchema = z.object({
  sub: z.string().uuid(),
  act: z.string().uuid().optional(),
  currentCompanyId: z.string().uuid(),
  tokenVersion: z.number().int(),
});

// 💡 二維權限矩陣 JSON 防呆驗證 (包含 maskedFields)
export const ModulePermissionSchema = z.object({
  canReadOwn: z.boolean().default(true),
  canReadAll: z.boolean().default(false),
  canWrite: z.boolean().default(false),
  canApprove: z.boolean().default(false),
  approvalLimit: z.number().min(0).default(0),
  maskedFields: z.array(z.string()).default([]), // RULE-1.3 欄位級別遮蔽
});

export const EntityPermissionSchema = z.record(ModulePermissionSchema);
export const RolePermissionsSchema = z.object({
  entities: z.record(EntityPermissionSchema),
});
```

## 伍、 UI/UX 大師級操作體驗規範 (初學者與工地現場防呆)

### 1. 401 閒置登出與草稿無縫迫降 (Graceful 401 Fallback)
* 考量工地網路不穩與共用設備閒置，當前端 API 攔截到 `401 Unauthorized` 時，**嚴禁直接清空畫面或強制跳轉 (Redirect)**。
* 前端必須攔截錯誤，將畫面上尚未存檔的表單（如幾十筆明細的計價單）序列化並「迫降」至 `localStorage`。
* 隨後於當前畫面彈出「原地登入 Modal」。使用者輸入密碼成功後，系統自動將 `localStorage` 的資料無縫灌回表單 State，讓心血「原地復活」。

### 2. 多頁籤同步廣播防呆 (BroadcastChannel API)
* 財務人員經常同時開啟 5 個以上的頁籤對帳。為了避免單一頁籤觸發 401 登出時，導致所有頁籤同時重新導向引發瀏覽器當機。
* 前端必須實作 `BroadcastChannel`。當 A 頁籤觸發 401 時，廣播通知 B、C 頁籤同步凍結畫面並彈出登入框，實現全域防護同步。

### 3. 權限渲染不卡頓 (Optimistic UI for Permissions)
* 嚴禁每次點擊按鈕才向後端詢問權限。前端取得登入 Token 時，需同步將快取的扁平化權限寫入 Global State (Zustand)。
* 畫面渲染時，若無 `canApprove` 權限，核准按鈕必須「直接消失」或「反灰並顯示鎖頭」，落實視覺層級的最前線防呆。
