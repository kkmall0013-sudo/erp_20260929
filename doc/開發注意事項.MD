## 📌 第一章：資料庫欄位規範與單一真實來源 (SSoT) 鐵律

為了避免營造工程 ERP 隨開發時間推移而產生**「欄位混亂、重複命名、同義不同字、型別衝突或資料孤島」**的致命災難，資料庫建置必須遵從以下絕對規範：

### 1.1 唯一真實來源：`ERP全模組資料庫欄位與用途總表.md`
1. **嚴格對齊總表**：
   - 系統中所有資料表名稱（Table）、欄位名稱（Column）、資料型別（Type）、預設值與外鍵關聯，**必須 100% 嚴格依照根目錄之 `ERP全模組資料庫欄位與用途總表.md` 之定義設定**。
   - **嚴格禁止 AI 擅自發明、簡寫或重造輪子**！
     - ❌ **嚴禁錯誤示範**：總表已定義專案目標預算為 `budgetAmount`，AI 自作主張寫成 `targetBudget`。
     - ❌ **嚴禁錯誤示範**：總表已定義業主單位為 `ownerName`，AI 擅自命名為 `clientName` 或 `customerName`。
     - ❌ **嚴禁錯誤示範**：總表已定義工程名稱為 `name`，AI 擅自寫成 `projectName`。

### 1.2 新功能/新欄位之「三步通報與變更 SOP」（未經確認嚴禁動 code）
如果在後續開發新模組或擴充業務功能時，發現《ERP全模組資料庫欄位與用途總表.md》中**缺少某特定業務欄位**，**AI 絕對禁止直接在程式碼或 SQLite DDL 中擅自添加**！必須嚴格執行以下三步流程：

```
┌────────────────────────────────────────────────────────────────────────┐
│ 【步驟 1】主動通報開發者 (告知使用者)                                     │
│  向開發者說明：目前功能缺少什麼欄位？業務痛點為何？建議新增之英中文名稱為何？│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 【步驟 2】提出完整架構解決方案 (等待開發者確認同意)                       │
│  提案內容包含：欄位名稱、資料型別、預設值、是否需建立索引、是否影響既有過帳單據│
└───────────────────────────────────┬────────────────────────────────────┘
                                    │ (經開發者明確確認同意後)
                                    ▼
┌────────────────────────────────────────────────────────────────────────┐
│ 【步驟 3】優先更新總表文檔，再撰寫程式碼                                  │
│  先手動將該欄位規格填入《ERP全模組資料庫欄位與用途總表.md》對應實體中存檔，│
│  最後才允許在 src/db/sqlite.ts 或 TypeScript Interface 中寫入該欄位！   │
└────────────────────────────────────────────────────────────────────────┘
```

> **📌 宗旨**：確保《ERP全模組資料庫欄位與用途總表.md》永遠是全系統唯一且最新的權威法典，杜絕欄位精神分裂！

## 📌 第二章：資料庫底層設計與百萬級效能注意事項 (10 萬 ~ 100 萬筆十年不卡頓)

營造工程 ERP 運行 5~10 年後，各工區工項、採購詢比單、估驗明細與會計發票將累積數十萬至數百萬筆。**禁止直接 `SELECT *` 全部撈到前端渲染**，必須在建表與查詢時落實以下四大鐵律：

### 鐵律 1：資料庫「複合 B-Tree 索引」先分布局
- **痛點**：未建索引時，資料庫進行百萬筆全表掃描 (Full Table Scan)，每次查詢耗時 5~15 秒。
- **AI 實作規範**：
  1. 所有新建的單據表，**必須針對常用過濾與排序維度建立複合 B-Tree 索引**：
     ```sql
     -- 專案 + 狀態 + 日期 複合索引（搜尋複雜度 O(log N)，100 萬筆命中只需 20 次比對，< 0.01 秒）
     CREATE INDEX IF NOT EXISTS idx_po_project_status_date 
     ON purchase_orders (project_id, status, document_date DESC);

     CREATE INDEX IF NOT EXISTS idx_valuation_contract_period 
     ON valuations (subcontract_id, period_no, status);

     CREATE INDEX IF NOT EXISTS idx_checks_company_due_status 
     ON bank_checks (company_id, due_date, status);

     CREATE INDEX IF NOT EXISTS idx_audit_table_target 
     ON audit_logs (target_table, target_id, created_at DESC);
     ```
  2. 查詢語句一律附加 `LIMIT` 與 `OFFSET`，禁止一次拉取萬筆資料：
     ```sql
     -- 標準高效分頁查詢語法
     SELECT * FROM purchase_orders 
     WHERE project_id = ? AND status = ? 
     ORDER BY document_date DESC 
     LIMIT 50 OFFSET ?;
     ```

### 鐵律 2：前端「虛擬滾動 (Virtual Scrolling)」與分頁延遲載入 (Lazy Load)
- **痛點**：瀏覽器渲染超過 500 個 `<tr>` 就會開始延遲；超過 2,000 個 DOM 會導致滑鼠滾輪卡頓；10 萬個 DOM 會直接造成瀏覽器分頁記憶體爆炸 (Out of Memory 崩潰)。
- **AI 實作規範**：
  1. 長清單表格（如工料明細、歷史單據、傳票清冊），**前端可見區域永遠只渲染當前螢幕可見之 25 ~ 40 筆 DOM 節點**。
  2. 滾動到底部時觸發增量載入，或搭配伺服器端分頁器（每頁 25/50/100 筆）。
  3. 前端常駐記憶體嚴格控制在 15MB 以內，確保滑動 100 萬筆與滑動 10 筆手感完全相同絲滑。

### 鐵律 3：營造業冷熱資料分離與結案封存 (Hot/Cold Data Archiving)
- **營造業特性**：95% 的日常操作（發包、估驗、開票）集中在「在建中工區 (佔全部資料 < 5%)」，已完工 3 年以上的結案案場僅供稅務查帳。
- **AI 實作規範**：
  1. 專案主檔與單據表內建 `is_archived INTEGER DEFAULT 0` 與 `is_deleted INTEGER DEFAULT 0`。
  2. 首頁個人儀表板、營運戰情大腦現金池、待辦審核等即時運算，**預設一律加上 `WHERE is_archived = 0 AND is_deleted = 0`**。
  3. 歷史封存案場進入「冷資料庫查詢模式」，不參與日常高頻運算，確保系統使用 10 年依然輕盈。

### 鐵律 4：聚合數據快照化 (Aggregated Summary Snapshots)
- **痛點**：每次進首頁若即時全表 `SUM()` 5 年來的上百萬張發票與估驗單，CPU 將持續滿載。
- **AI 實作規範**：
  1. 案場主檔維護 `actualCost` (已發包累計)、`committedCost` (已估驗累計) 等彙總欄位。
  2. 單據過帳時，透過交易事務 (Transaction) **即時以差額累加回寫快照池**，而非每次動態重算百萬筆歷史。

## 📌 第四章：營造工程內控防呆憲法 (Zero-Flaws Rules)

營造業涉及龐大發包金額與工班計價，AI 實作任何功能時必須遵守以下防弊鐵律：

### 1. 全域零負數鐵律 (Pink Deduction UI)
- 資料庫內所有折讓、下包代購扣款、安全違規扣點、變更設計追減項，**數值必須以「正數」儲存**，計算總額時由公式統一減除。
- 前端介面一旦偵測到減項沖銷（`isDeduction = true`），一律強制套用**櫻粉色柔和警示外觀 (`bg-rose-50 border-rose-200 text-rose-800`)**，醒目標示以防重複多扣或少扣。

### 2. 過帳實體快照 (Frozen Snapshot)
- 單據（報價單、採購單、估驗請款單、應收付傳票）一旦按下「核准過帳」，**其交易對象名稱、統編、案場全名、核定單價與稅率即刻凍結成快照字串**。
- 未來即使商業夥伴更名或稅率調整，已過帳的歷史單據嚴禁連動篡改，維持不可破壞之法律效力。

### 3. 沙盒與 iframe 友善 (嚴格禁止原生 window.confirm)
- 由於系統常運行於預覽環境、沙盒或 iframe 中，**瀏覽器原生 `window.confirm()` / `window.alert()` 會被瀏覽器強制靜默回傳 `false`**，導致使用者點擊刪除按鈕時毫無反應！
- **AI 實作鐵律**：所有刪除、核准、駁回或危險操作，**一律使用 React 客製化高階防呆確認 Modal**，顯示受影響之單號、金額與同仁姓名，點擊確認後執行。

### 4. 三層身分與 2D 矩陣 PBAC (權限架構)
- **Tier 1 - 唯一最高 Superadmin**：全系統僅限 1 位，享金身保護，禁止刪除、停用或改為其他角色，交接須本人親簽。
- **Tier 2 - 管理員 Admin (若干位)**：負責帳號分發與工區權限維護，受防呆邊界保護，禁止刪除其他 Admin。
- **Tier 3 - 一般同仁 User**：支援 **2D 矩陣多群組同時指派**（例如同時擁有工務組與業務組）。權限採聯集 (Union)，單筆審批額度自動取所屬群組中之**最大值 (Max Approval Limit)**。

### 5. 雙軌設定分離憲法 (Software App Config vs Business Legal Config)
- **Superadmin 專屬：軟體程式設定 (App Engine Config)**：
  - 專管「這套軟體程式本體」，與客戶公司之日常業務、財務法規徹底解耦。
  - 涵蓋範圍：軟體品牌名稱（如「田頭」頂欄標題）、副標題（「A1 商務應用雲」）、版本號（「v2.5.0-PRO」）、HTML分頁標題、頁腳版權宣告、全模組開放授權開關 (`APP_ENABLED_MODULES` Feature Flags)、全域緊急公告廣播條、維護模式等。
  - 介面權限：僅限 `isSuperadmin` 登入時才可看見與操作；Admin 與一般同仁登入後連此選單與設定均完全隱藏。
- **Admin 專屬：基本資料營運法規中樞 (Operation & Legal Config)**：
  - 將原獨立之【公司設定】正式合併整併入【基本資料 (SETTINGS)】，使導航選單極致簡潔洗鍊。
  - 介面採清晰五大階層分頁（Tabs）：
    1. `[營運法人實體]`：集團母體、子公司統編、地址、負責人、電話帳戶等組織主檔。
    2. `[法定稅制與健保]`：
       - 法定營業稅率 (%)、二代健保補充保費率 (%)、發票尾差容差 (元)、法定最低基本工資 (元，如現行 28,590 元 / 時薪 190 元)。
       - **法規預約排程生效日機制 (Scheduled Effective Timestamps)**：支援輸入「實施生效時間戳記（精確至分秒，如 `2027-01-01 00:00:00`）」，新法規到期平滑自動生效，免除管理人員在生效當天凌晨 0 時起床修改之負擔。
    3. `[工程合約與預算內控]`：
       - 預設估驗保留款扣留率 (%)、超支預算防呆模式 (STRICT / WARN)。
       - **預設請款票期開關**：支援天數輸入或一鍵關閉票期（`無票期 · 即期付款 / 現金電匯`，天數歸零或標記停用）。
    4. `[單據跳號規則]`：
       - 各業務單據前綴與流水號計數器維護。
       - **嚴格不可回溯鐵律**：校正時嚴禁回退至小於等於資料庫現存最大單號，杜絕重號；允許往後跳號；產號引擎主動防碰撞自癒。
    5. `[資料庫安全與歸檔備份]`：
       - **實體化內嵌面板，禁止空按鈕**！涵蓋：① 12 大模組即時健康度與資料量；② 2010～2026 歷年封存快照清冊；③ 時段過濾模組化備份還原工具；④ 全庫快照下載與 SQL Dump。
  - **動態法規解耦鐵律 (Dynamic Regulatory Zero-Hardcode Rule)**：
    - **嚴格禁止 AI 與工程師在程式碼中寫死（Hardcode）稅率 5%、健保 2.11%、保留款 10%、基本薪資等數值**！
    - 所有業務計算邏輯一律由 `system_configs` 動態讀取。
    - 當立法院修法或公司內控調整時，Admin 登入基本資料介面修改數字或預約生效排程，即可全系統無痛切換，不需 Superadmin 介入，亦不需修改任何一行程式碼。

## 📌 第五章：模組開工推進標準 SOP (AI 開發 Checklist)

後續各業務模組（專案案場、商業夥伴、報價 CPQ、採購發包、估驗計價、財務會計等）開發時，**必須單一模組聚焦推進，完成測試後方可掛載至選單**，請依照以下標準步驟進行：

1. **Step 1 - 查核《ERP全模組資料庫欄位與用途總表.md》**：
   - 嚴格依照總表對應章節之欄位名與型別宣告 DDL，**若需新欄位必須先向開發者提報並更新總表**。
2. **Step 2 - 建立複合 B-Tree 索引**：
   - 於 `src/db/sqlite.ts` 加入主鍵、外鍵、版本號與專屬複合索引。
3. **Step 3 - 嵌入 RIGHT 主工作子視窗**：
   - 掛載至 `RightSubWindow.tsx`，保持 `overflow-y-auto` 獨立滾動，頂部鎖定工具列。
4. **Step 4 - 大數據分頁與虛擬滾動防護**：

   - 確保新表資料能被「一鍵匯出 .sql」、「下載 .sqlite」與「年度唯讀封存快照」完整包含與還原。

## 📌 第六章：資料庫年度封存、附件相對路徑與冪等還原工程規範

### 6.1 年度唯讀封存快照 (Annual Archival Snapshots)
1. **主庫常駐與年度死資料截斷**：
   - 營造 ERP 運作時，主要運作庫 (`database.sqlite`) 平時保留所有完整資料，不擅自截斷在建中案場。
   - 每年底結算完成後，系統一鍵或自動產出獨立的 SQLite 實體檔（如 `ERP_ARCHIVE_2025.sqlite`），內部標記 `isSealed = 1` 並設為唯讀 (`PRAGMA query_only = ON;`)，永久不可篡改。
2. **三大業務落地場景**：
   - **場景 A：免啟動主系統之靜態離線查詢**：
     - 使用者若需調閱 5 年前某歷史案場，可直接透過系統「歷史庫檢視器」以唯讀模式掛載該年度檔案，獨立搜尋，極度輕量且不干擾正式運行庫。
   - **場景 B：新電腦系統搬遷選擇性載入**：
     - 安裝新機全新乾淨系統時，使用者可勾選載入「近 5 年或 10 年」之封存包，過於久遠的歷史包留在離線隨身硬碟備查，使新系統維持最輕巧高效。
   - **場景 C：災難應急復原**：
     - 若遭遇勒索病毒或硬碟毀損，各年度封存檔可作為不可竄改之時間節點基底。

### 6.2 附件實體與資料庫徹底分離鐵律 (Relative Path & Vault Architecture)
1. **資料庫永存輕量中繼資料**：
   - 資料庫表 `SystemFile` 嚴禁使用 BLOB 存放大圖或 PDF，永遠只存相對存放路徑 (`storagePath`) 與 SHA-256 指紋 (`fileHash`)。
   - 資料庫本體純文字數字永遠維持在數十 MB 內，隨身碟一秒打包帶走。
2. **相對目錄結構分流**：
   - 程式根目錄專屬 `storage/` 儲存池：
     - `storage/public_docs/`：非敏感文件（現場施工照片、工務日報、CAD 圖說），依 `YYYY/MM/` 分層儲存。
     - `storage/secure_vault/`：機敏文件（底價標單、合約原件、薪資明細），強制以 **AES-256-GCM 對稱加密** 存成 `.enc` 二進位檔，讀取時由後端金鑰即時串流解密。
   - 系統整包搬遷到新電腦時，直接複製專案與 `storage/` 資料夾，相對路徑 100% 保持有效不斷鏈。

### 6.3 毫秒級時間戳記與還原狀態機鐵律 (Idempotent Restore State Machine)
1. **身分唯一判定（UUID / 毫秒業務單號）**：
   - 解決同一毫秒多筆支出（如同一秒有兩筆 5,000 元合法支出）：每筆資料以全域唯一 `id`（UUID v4 或毫秒序號）為唯一身分識別，絕不因金額、日期相近而誤判或吞單。
2. **三柱版本樂觀鎖還原狀態機**：
   - 全單據與明細皆具備 `id`、`createdAt` (毫秒)、`updatedAt` (毫秒)、`version` (整數)。
   - 還原備份檔時，比對目標資料庫同 `id` 資料：
     - **狀況 1 (無此 ID)**：`INSERT` 全新寫入。
     - **狀況 2 (ID 已存在且備份檔 version == 主庫 version)**：`SKIP` 跳過不寫入（防重複）。
     - **狀況 3 (ID 已存在且備份檔 version > 主庫 version)**：`UPDATE` 覆蓋更新（修正版生效）。
     - **狀況 4 (ID 已存在且備份檔 version < 主庫 version)**：`IGNORE` 略過（主庫資料更新）。

### 6.4 四大漏洞排查與工程防禦鐵律 (Hardened Safeguards)
1. **外鍵相依衝突防護 (Topological Dependency & FK Safety)**：
   - 還原寫入作業強制依照拓撲依賴順序執行：`系統參數與法人主檔` ➔ `專案與夥伴廠商` ➔ `合約與採購單` ➔ `估驗計價與會計憑單` ➔ `附件與日誌`。
   - 批次還原事務期間暫時關閉外鍵約束，全數寫入後立即執行 `PRAGMA foreign_key_check;`，確認全域關聯 100% 完整後才提交事務 (Commit)。
2. **單據跳號計數器自癒校準與防回溯鐵律 (Sequence Reseed & Anti-Rollback Rule)**：
   - **禁止回溯校正**：嚴格禁止使用者或程式將計數器修改為小於等於資料庫現存最大單號的值。允許往後跳號（如 002 改為 005），但嚴禁往前回溯，防止重號錯亂。
   - **產號主動防碰撞**：`getNextSequenceNumber` 產號時若遇已存在單號，自動跳號直至空號。
   - **還原後自動自癒校準**：任何資料庫還原完成前，系統底層強制自動掃描各業務單據表之當前最大流水單號。若資料庫內既有最大號大於 `document_sequences.currentVal`，自動將計數器更新為最大號，徹底杜絕還原後下一張新單據撞號衝突。
   - **實體表底層唯一約束**：所有業務單號欄位（`apNumber`, `poNumber`, `arNumber`, `valuationNumber` 等）強制設置 `UNIQUE NOT NULL` 約束。
3. **年度封存自包含一致性快照 (Self-Contained Snapshot)**：
   - 年度封存切片產出時，除了封存該年度發生的估驗、收付與單據外，該單據關聯之上游專案合約與廠商主檔摘要一併連帶打包入封存檔。
   - 保證獨立開啟該年度歷史封存 SQLite 檔時，所有關聯單據名稱與合約金額完整自洽，絕不出現關聯斷裂的空值。
4. **POSIX 標準相對路徑格式 (Path Normalization)**：
   - 資料庫中 `SystemFile.storagePath` 一律強制以 POSIX 正斜線 `/` 存儲（如 `storage/public_docs/2026/10/uuid.pdf`），嚴禁 Windows 系統反斜線 `\` 污染資料庫。
   - 後端讀取檔案時透過標準路徑函式解析，確保從 Windows、Mac 到 Linux 伺服器搬遷時 100% 相容有效。

## 📌 第八章：Phase 3 商業夥伴模組實務規範與防呆鐵律

商業夥伴模組為全 ERP 的交易對象基石，AI 與開發人員在實作本模組時必須嚴格遵守以下業務規則：

### 8.1 業主 vs 廠商頂部雙頁籤視圖 (Dual-Tab Architecture)
1. **雙頁籤切換**：頂部明確提供 `[業主名冊 (Clients)]` 與 `[合作廠商 (Vendors)]` 雙頁籤切換，不另開無意義的獨立頁面。
2. **各自獨立專屬業務欄位**：
   - 業主名冊：側重合約付款條件、請款窗口、專案業主全稱、統編、統一發票開立需求。
   - 合作廠商：側重工項服務多層級分類、匯款金融帳號、收發支票資訊、評鑑等級與黑名單警示。
3. **一鍵自廠商引薦/加入變業主 (One-Click Vendor-to-Client Conversion)**：
   - 實務上對方可能身兼協力廠商與發包業主。業主名冊視圖中**提供「搜尋現有合作廠商並一鍵加入變業主」按鈕**。
   - 點選後直接帶入該廠商之統編、名稱、電話、地址與基本資料，自動賦予業主身分，落實單一事實來源 (SSoT)，杜絕人工重複鍵檔出錯。

### 8.2 合作廠商服務項目：多層級下拉式選單 (Hierarchical Dropdown)
1. **版面純淨整潔**：嚴禁在畫面上堆疊數十個彩色標籤 (Tags) 造成視覺污染。
2. **階層式篩選**：採用清晰的二階/三階「多層級下拉式選單」（如：第一階【結構工程】➔ 第二階【模板工項】/【鋼筋工項】；第一階【裝修工程】➔ 第二階【泥作貼磚】/【油漆塗裝】），便於精準過濾與派工發包。

### 8.3 企業實務多地址、多電話、多聯絡人架構
1. **多地址支援 (`PartnerAddress`)**：
   - 考量法人公司常有「公司登記地址」、「工廠廠區地址」、「工務所聯絡地址」等多重地點。
   - 系統支援動態增刪多筆地址。介面直接標示「地址」，**預設一律為通訊地址**（無須刻意拆分通訊/戶籍，但保留欄位型別擴充性）。
2. **多電話與多聯絡人 (`PartnerContact`)**：
   - 支援總機電話、傳真、業務窗口、工務窗口、會計窗口等多組聯絡人資訊與備註。

### 8.4 金融帳戶、支票資訊與手續費內控鐵律
1. **金融機構代碼標準下拉**：
   - 內建台灣銀行代碼清冊（包含總行 3 碼代碼、銀行名稱、分行 4 碼代碼/名稱），下拉選單支援代碼與中文快速模糊搜尋，防止出納匯款帳號打錯。
2. **手續費（匯費與郵費）預設公司自行吸收**：
   - 營造工程實務慣例：廠商請款 100 元即全額支付 100 元，匯費與支票郵寄掛號費由本公司自行吸收。
   - `bankFeePayer` 欄位**預設為 `COMPANY`（公司負擔）**，財務出納不內扣請款廠商金額。
3. **收發支票帳務資訊完整留存**：
   - 系統支援記錄收受與開立之支票資訊：付款銀行、帳號、支票號碼、發票/開票日期、到期日、抬頭、禁止背書轉讓標記。
4. **原始單據與憑證影像留存 (附件對接規範)**：
   - 存摺封面照片：出納必備核波依據，上傳後支援即時縮圖與全螢幕放大檢視。
   - 收發支票影印/掃描本（含 PDF 格式）：支援預覽與留存備查。
   - 資料庫端透過標準 `FileLink` / `SystemFile` 結構關聯，預留給 Phase 9 檔案管理模組對接。

### 9.4 💳 票據法規實務與到期日計算規範
- **票據法與實務三大日期節點 (SSoT)**：
  1. **收票日 / 簽收日 (`receivedDate`)**：出納收到或寄發支票之實際交付日期。

- **票據法第22條第1項一年消滅時效**：

  - 支票登記視窗提供快捷一鍵填入兌現日：【見票即付 (同開票日)】、【30 天期】、【60 天期】、【90 天期】與【法定一年時效】。

## 📌 第十章：單據編碼規則、防重號架構與資料庫全庫備份還原一致性規範

### 10.1 單據編碼與自動產號中樞的架構定位與存在意義
1. **核心業務痛點與價值**：
   - 營造工程單據繁多（採購詢價、採購單、估驗計價、應付帳款、應收發票、支票），若讓同仁手動輸入單號，必定產生**跳號、漏號、撞號與主鍵衝突**。
   - 單據編碼中樞（`document_sequences` 與 `document_sequence_rules`）之唯一核心任務：**「制定各模組編碼規範」**與**「提供原子化無感自動配號與防重自癒 (`getNextDocumentNumber`)」**。
2. **歷史已結案月份歸檔抽屜去除原因**：
   - 過往月份（如 202603、202604）的會計單據早已入帳申報，屬法定會計憑證，在編碼中樞中屬於不可修改之歷史；若展示 10 年唯讀抽屜，只會塞滿無效資訊並干擾規則制定。
   - 因此日常維護聚焦於「當期（本月）開單進度」與「下月預約號碼」，其餘歷史移入 Superadmin 專屬之「舊系統匯入防撞審計」。

### 10.2 模組前綴變更與唯一性防衝突機制 (`validateDocumentPrefixConflict`)
1. **全域唯一性鎖定（嚴禁跨模組重疊）**：
   - 系統各業務模組前綴（如 `AP`、`AR`、`PO`、`VAL`、`PRJ` 等）必須全域唯一。
   - 若使用者嘗試將 `AP` (應付帳款) 改為已存在的 `AR` (應收帳款)，`validateDocumentPrefixConflict` 立即在前端即時攔截並停用儲存按鈕，杜絕主鍵跨表衝突與帳務混淆。
2. **前綴變更平滑過渡（以 `AP` 變更為 `PP` 為例）**：
   - 歷史單據（如 `AP-202603-001`）作為法定憑證**永久保留原樣、絕不竄改**。
   - 變更生效後新開立之單據自新前綴第一號（如 `PP-202610-001`）開始接續配號。
3. **格式強規範防呆**：
   - 強制 1~8 碼大寫英數字，禁止空格與特殊符號（連字號由 `delimiter` 欄位獨立控制），杜絕 SQL 與系統解析錯誤。

### 10.3 雙角色視圖分流機制 (Admin vs Superadmin)
1. **Admin 業務主管視角**：
   - 純粹的「公司單據編碼規範制定表」：僅呈現單據名稱、前綴格式、當前配發預覽、下月預約號碼及編輯按鈕，無任何底層資料庫或技術雜訊。
2. **Superadmin 程式設計師深度維護視角**：
   - **底層指針即時監控 (DIAGNOSTICS)**：檢視 SQLite `document_sequences` 資料表中實際之 `currentVal`、`nextVal` 與實體表現存最大流水號。
   - **歷史舊單匯入防撞審計 (LEGACY_AUDIT)**：當從舊系統遷移歷史舊單時，清楚揭露各期別已使用之最大流水號與防撞門檻建議。
   - **備份還原一致性指針重置 (BACKUP_CONSISTENCY)**：在執行資料庫還原或冷備份掛載後，提供一鍵 `reseedDocumentSequences()` 自動重置全庫指針。

### 10.4 全庫資料庫備份與直接還原一致性規範
1. **頂部導航 (TopSubWindow) 與基本資料 (BasicSettingsHubWorkspace) 雙通道 100% 統一**：
   - 統一提供五大標準功能：① 全庫檔案一鍵上傳還原、② 下載 SQLite 快照 (.sqlite)、③ 匯出全庫 SQL 指令稿 (.sql)、④ 歷史封存與進階管理中心、⑤ 重設出廠預設種子。
   - 統一支援 `.sqlite` / `.db` 二進位實體資料庫檔案與 `.sql` 純文字指令檔一鍵拖曳或點選上傳。
2. **還原前防呆與自動格式偵測**：
   - 上傳檔案後自動判讀檔案類型與大小，提示全庫覆蓋安全提醒，並提供「還原前先下載當前庫備份防呆 (建議)」按鈕。
3. **還原後自動流水號校準對齊 (`reseedDocumentSequences`)**：
   - 不論是上傳 `.sqlite` 或是執行 `.sql` 還原，系統完成資料庫掛載後**自動執行全模組單據流水號校準**，自動將計數器推升至目前現存最大單號 + 1，保證還原後同仁開立新單 100% 不撞號。

### 1. 建造物類型自訂兩階層字典架構 (`BUILDING_CATEGORY_TREE`)
1. **痛點與設計背景**：
   - 原先硬編碼的建造物類型無法滿足各營造廠或轉型不同行業之工程型態（如鐵皮倉庫、鋼構建築、農業設施、風雨球場、鋼梯、屋頂浪板等）。

2. **資料庫儲存與結構**：
   - 儲存位置：SQLite `system_configs` 資料表，鍵名：`BUILDING_CATEGORY_TREE`。
   - 資料模型：
     ```typescript
     interface BuildingCategoryItem {
       id: string;
       name: string;
     }
     interface BuildingCategoryGroup {
       id: string;
       name: string;
       items: BuildingCategoryItem[];
     }
     ```
3. **二階選取約束規範**：
   - 表單選擇時（例如案場新建與編輯），使用 HTML5 `<optgroup>` 或自訂階層選單。

4. **專屬管理介面 (`BuildingCategoryManagerModal`)**：
   - 於案場管理頁面提供「類型維護」按鈕開啟管理對話框。
   - 支援大分類的新增、重新命名與刪除。
   - 支援各大類下小項目的即時新增、刪除。
   - 具備防呆機制（刪除大類前需清空或確認連帶小項），並提供一鍵還原預設樣板功能。

### 2. 預計協力廠商發包預算主表 (`project_budget_partners`)
1. **痛點與設計背景**：
   - 案場成立初期需要進行發包規劃，預估將使用甲廠商多少料、乙廠商多少料。
   - 當案場進入執行階段叫料時，協力廠商常因工期冗長忘記及時請款，導致財務查帳困難。
   - 需要建立獨立的預算廠商表，並可與後續進貨、計價付款連動統計。
2. **資料表定義與索引**：
   ```sql
   CREATE TABLE IF NOT EXISTS project_budget_partners (
       id TEXT PRIMARY KEY,
       project_id TEXT NOT NULL,
       partner_id TEXT,
       partner_name TEXT NOT NULL,
       category TEXT,
       estimated_amount REAL DEFAULT 0,
       notes TEXT,
       created_at TEXT DEFAULT CURRENT_TIMESTAMP,
       updated_at TEXT DEFAULT CURRENT_TIMESTAMP
   );
   CREATE INDEX IF NOT EXISTS idx_budget_partners_project ON project_budget_partners(project_id, partner_id);
   ```
3. **核心欄位用途**：
   - `project_id`：關聯之案場主鍵。
   - `partner_id`：協力廠商 ID（若已於主檔建立或由快選挑選），若僅為臨時記錄可為廠商名稱。
   - `partner_name`：廠商公司名稱（唯一定位標識）。
   - `category`：發包工料類別（如鋼材、混凝土、拆圖等）。
   - `estimated_amount`：案場預估發包/叫料金額。

### 4. 懸浮式選單防裁切架構 (Floating Portal Architecture)
1. **痛點與排版陷阱**：
   - 傳統下拉選單若採用 `relative` / `absolute` 定位，當父層容器存在 `overflow-x-auto`（如響應式資料表格）或 `overflow-y-auto`（如 Modal 滾動區塊）時，**下拉選單會被父層容器強制裁切遮蔽（Clipping）**，導致使用者無法選取下方的項目。
2. **全系統解決方案標準**：
   - **React Portal 脫離 DOM 樹**：一律使用 `ReactDOM.createPortal(dropdownElement, document.body)` 將選單 DOM 直接掛載於 `document.body` 最外層。
   - **動態座標計算**：
     - 利用 `triggerRef.current.getBoundingClientRect()` 於點擊時取得觸發按鈕在可視視窗（Viewport）中的 `top`、`bottom`、`left`、`width`。
     - 選單使用 `position: fixed`，並計算精確的 `top = rect.bottom + 4`、`left = rect.left` 與對應 `min-width`。
   - **層級保證**：設定極高層級 `z-[99999]`，徹底突破一切彈窗、遮罩與滾動區域。
   - **事件連動**：
     - 視窗大小改變（`resize`）或頁面滾動（`scroll` capture）時自動重新計算或關閉選單，避免選單浮空錯位。
     - 點擊外部（`click outside`）與按下 `Escape` 鍵立即安全關閉。
   - **標準組件**：
     - `FloatingSubcontractorSelect.tsx`：二階協力廠商專用浮動選單。
     - `PartnerSearchSelect.tsx`：業主與全系統合作夥伴搜尋浮動選單。

### 5. 進貨與請款（計價）連動唯讀對帳引擎
1. **資料流原則（Read-Only Compilation）**：
   - 案場端對進貨與付款資料**僅作查詢與彙整顯示，嚴禁反向修改進貨端或財務端資料**。
   - 資料聚合來源：
     - `inbound_receipts`：以 `project_id` 與 `partner_id` 彙整進貨明細及進貨總金額。
     - `valuations` / `accounts_payable`：以相同條件彙整累計計價請款與已支付金額。
2. **待請款差額檢警機制 (Pending Billing Alert)**：
   - 計算公式：
     $$\text{待請款差額} = \text{累計已進貨金額} - \text{累計已請款(已支付)金額}$$
   - 當 $\text{待請款差額} > 0$ 時，於案場廠商清單與彙總卡片中，即刻高亮提示「待請款」琥珀色標籤，並標註差額數值。
   - 解決實務上協力廠商因忘記請款、而工程現場或財務人員又無從迅速察覺的重大管理漏洞。
3. **案場廠商獨立穿透檢視 (`ProjectVendorInboundModal`)**：
   - 點擊預計協力廠商列表中的「查看進貨明細」或進貨統計時，彈出專屬穿透彈窗。
   - **嚴格實施雙條件隔離過濾**：
     `receipt.projectId === currentProject.id && receipt.partnerId === selectedPartner.id`
   - 只顯示該案場所屬之進貨料號、品名規格、數量、單價、進貨日期與簽收人，絕不混入該廠商供應其他案場之任何貨物，杜絕資料混淆。

## 第十三章：聯絡明細模組重構、業主/廠商版面分流與資料庫欄位整合規範

### 1. 模組名稱正名為「聯絡明細」與去除裝飾雜訊
1. **導航與頁面正名**：
   - 左側導航、頂部標題、名冊清單全面由「廠商工班」正名為 **「聯絡明細 (Business Partners)」**。
   - 兼具 CRM（業主客戶名冊）與 SRM（協力廠商工班名冊）之單一核心資料源 (SSoT)。
2. **移除無關功能連結**：
   - 徹底拔除模組內「通用小程式專區」跳轉按鈕與對應無關 Modal，釋出工具列空間配置實用的業務操作（「專業分類管理」、「批次匯入」、「匯出 CSV」）。

---

### 2. 業主與廠商版面徹底分流與身分證/統編驗證防呆
1. **個人自建/自住業主免強制填寫統一編號/身分證字號**：
   - 自然人自建案場或個人自住房產裝修業主，實務上多不具備統一編號，且因個資考量未必即刻提供身分證。
   - **驗證約束調整**：當 `isIndividual = true` 或 `entityType = 'NATURAL_PERSON'` 且身分為業主客戶時，統一編號/身分證字號欄位設定為非強制（選填）。
   - 若使用者留空，系統直接通過儲存；若使用者填寫，則仍啟動 10 碼台灣身分證字號或 8 碼公司統一編號格式加權邏輯檢核，確保輸入品質。
2. **業主編輯器頁籤自動精簡過濾**：
   - 當編輯之夥伴為純業主（`isCustomer && !isVendor`）時，系統自動收折隱藏以下與業主無關之頁籤：
     - `CATEGORY`（多元工種服務）
     - `BANK`（金融帳戶與存摺）
     - `CHEQUES`（支票往來記錄）
   - 僅呈現基本身分、通訊/案場地址、聯絡人、名片管理與圖說合約無紙化金庫，大幅降低鍵檔認知負擔。

---

### 3. 業主兼任合作廠商（補填廠商資料）引導流程 (`ClientUpgradeVendorModal`)
1. **業務痛點**：
   - 部分案場業主本身為工程背景，或於施工期間兼任某些建材供料（如地主供料、水電工班自建兼包工）。
   - 傳統作法容易在廠商名冊重新新增一筆重複資料，破壞 SSoT 單一事實原則。
2. **引導補填與原子升級機制**：
   - 業主名冊之表格列與名片卡片底部提供「兼任廠商 / 補填廠商資料」按鈕。
   - 點擊後開啟引導視窗，系統自動帶入業主既有名稱與聯絡電話，並主動提示補填缺少的：
     ① 主要工料類別與細部工種；
     ② 領款銀行代碼、分行與存摺帳號；
     ③ 統一編號（若先前留空）。
   - 點擊「確認升級為合作廠商」後，後端將該主檔更新為雙重身分（`isCustomer: 1, isVendor: 1, type: 'BOTH'`），立即在業主與合作廠商雙邊名冊連動呈現。

---

### 4. 廠商第一階及第二階專業分類樹狀字典管理 (`SUBCONTRACTOR_CATEGORY_TREE`)
1. **字典共享與權限控管**：
   - 儲存於 `system_configs` 之 `SUBCONTRACTOR_CATEGORY_TREE`。
   - 權限約束：限 `SUPERADMIN`、`BOSS`、`ADMIN` 或具備系統參數特許權限（`canManageSystemConfigs`）之人員維護。
   - 與案場工程模組之預算協力廠商發包下拉選單 100% 共享同步。
2. **資料庫欄位整合對齊**：
   - `business_partners` 表擴充三個關鍵欄位：
     - `isIndividual INTEGER DEFAULT 0`：標記是否為自然人/個人業主。
     - `categoryMain TEXT`：第一階主要專業工料大類。
     - `categorySub TEXT`：第二階細部專門工種名稱。
   - 確保日後案場工程模組發包預算與派工排程可直接無縫關聯夥伴主檔。

---

### 5. 名冊批次 CSV 匯入與匯出規範
1. **CSV 匯出標準（防 Excel 亂碼）**：
   - 匯出內容強制於首字節寫入 UTF-8 BOM (`\uFEFF`)，相容微軟 Excel 雙擊直接開啟繁體中文。
   - 欄位包含：夥伴編號、夥伴名稱、業務身分、實體型態、是否個人、統編/身分證、主要聯絡人、聯絡電話、Email、地址、工項大類、細部工種、銀行代碼、銀行名稱、銀行帳號、戶名、付款天數、高風險夥伴、風險原因。
2. **CSV 批次匯入檢核與範本下載**：
   - 提供標準 CSV 空白範本下載，內建清楚填表說明。
   - 支援拖曳 `.csv` 上傳，自動解析並執行欄位型態檢核（名稱必填、業務身分識別、統編長度檢查）。
   - 匯入預覽畫面即時標註「將新增」或「將更新」狀態，確認無誤後採原子交易執行批次寫入，並自動計入全域審計日誌。
